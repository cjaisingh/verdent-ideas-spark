# AWIP Dashboards, Reporting & Data Extraction Framework

**Version:** 1.0 — 4 July 2026 — Status: Proposed. One framework governing every way a number or artefact leaves AWIP's tables and reaches a human or another system — live dashboards, rendered reports, data extraction — across operator, client (FM7+) and machine consumers. The pieces exist but grew organically (widget registry, ~15 admin pages, HTML-report pattern, COBie export, close packets, fidelity panel, XLSX exports); the framework makes every new module inherit them at near-zero cost.

## 1. Seven principles
1. **Views over state; no AI in numbers.** Every figure comes from a deterministic SQL view/mart. AI may narrate (labelled, pickModel()-routed), never compute a number. 2. **Every number is a question you can ask.** Drill-down to provenance mandatory: metric → view → rows → lineage/anchors. A number that can't explain itself doesn't ship. 3. **Approval-aware by construction.** Nothing below a surface's min_approval_state appears client-facing; enforced in the resolving layer, not the UI. 4. **Freshness displayed, never implied.** Every widget/section/manifest carries as_of + cadence context; stale-beyond-cadence renders amber. 5. **Engagement-scoped, always.** Client surfaces resolve tenant from the JWT claim, never parameters. 6. **Deterministic and diffable.** Stable ordering and IDs so re-runs diff cleanly (the COBie rule, generalised). 7. **Everything that leaves is evented.** Report runs, export runs, signed-URL mints, FM pushes — one event row each with actor, scope, content hash. Extraction without a trail is exfiltration.

## 2. Three layers
Layer 1 SEMANTIC (define): metric_definitions + marts — one place a metric is defined. Layer 2 PRESENT: dashboards (live, pull) and reports (rendered, push). Layer 3 DELIVER: extraction — file exports, contract API reads, FM pushes, offboarding archives, DSAR packs. A module that defines metrics in Layer 1 gets Layers 2–3 nearly free; a surface bypassing Layer 1 is a bug.

## 3. Layer 1 — metric registry
metric_definitions: key (e.g. fm3.kr_variance_pct, twin.coverage), owner_module, title, description, view_name (the ONLY place the number is computed), unit, grain, freshness_cadence_minutes + stale_multiplier, min_approval_state (client-visibility floor), audience operator/client/external, provenance_rule (facts/events/work_log/decisions), version (bump on semantic change — old retired, never edited); metric_definition_events append-only. **Rules:** views are security_invoker (RLS flows through) reading canonical tables/marts only; dashboards pin versions; existing marts register retroactively (inventory-as-audit); CI scripts/check-metric-registry.ts fails builds where a widget or report section references an unregistered view.

## 4. Layer 2a — Dashboards
Reuse the shipped chassis (per-user tabs, bento templates, WidgetRegistry, debounced persistence); upgrade the widget contract: a generic MetricWidget {metricKey, grainFilter, presentation stat/trend/bar/table/status, drill} resolves the registry → view → data; freshness badge + as_of rendered by the wrapper, not each widget. **Three tiers:** operator/platform (existing /dashboard + admin; may show any-lifecycle with badges; realtime via unique-per-mount channels); client (FM7 portal panels — fidelity, FM3 performance, FM5 workflows, FM12 ops, later FM8 portfolio; every panel a client_surfaces row; tenant from JWT; approved floor); external/procurement (/trust-style — published posture only, a page tier not a dashboard tier). Every dashboard surface registers in observability_registry (surface_kind='dashboard') so abandoned dashboards show up as stale inventory.

## 5. Layer 2b — Reporting
The HTML-report pattern promoted to framework. report_kinds: key (fm3.period_pack, close.month, qbr.quarterly, shadow.promotion, twin.fidelity, deep_audit.weekly…), owner_module, renderer (_shared/report-renderers/), sections (ordered metric keys + narrative slots), schedule (cron | on-demand, rides W8.1 kind report.render), audience, formats html/xlsx (pdf later), retention_policy. report_runs: kind, tenant, period_ref, status, storage_path, content_sha, **metrics_snapshot jsonb (the numbers AS RENDERED — a report is a record; re-opening next quarter shows what was said; regeneration is a new run)**, narrative_model (ai_component_versions ref), rendered_at, requested_by. Narrative sections optional, labelled, citing the metrics they narrate; the narrator is a registered ai_component (a QBR prompt change walks the shadow ladder). Distribution is a separate concern: v1 signed-URL on demand; push arrives with FM6 reading report_runs, never re-rendering. Existing reports migrate in (deep-audit, reviews, close packet, QBR); FM3 packs, shadow reports and deletion certificates are born native.

## 6. Layer 3 — Extraction
Five shapes, one discipline (evented, idempotent, approval-aware, deterministic, engagement-scoped): file exports (COBie, XLSX registers, report downloads — export_runs row, signed URLs from private buckets, approval filter baked into the generating view); contract API reads (api_call_logs; client tokens never see cross-tenant rows); FM-tool pushes (S6 — idempotent per (tool, external_id, field, value_hash), fm_push_events, DLQ sentinel, only approved export_pending winners push); offboarding archives (§C5 — what leaves at the end proves the others were scoped); DSAR packs (S2.6 + redactor). export_runs: kind, tenant_id, scope, status, storage_path, content_sha, row_count, requested_by. **The one hard line:** no extraction reads raw tables ad hoc — every export generates through a registered view or renderer, where approval filtering, redaction and tenant scoping live, so a new shape can't accidentally skip them. Sentinel export_anomaly (medium — a tenant's export volume >3× its 30-day median).

## 7. The drill-down contract
Every metric's provenance_rule resolves to one shared drawer pattern: facts (→ contributing canonical_facts → lineage → source document + anchor), events, work_log, decisions. Client surfaces get the same drawers approval-filtered — a client drills a variance to the approved facts behind it and stops there. The fidelity panel is just four registered metrics with facts-pattern drills.

## 8. Adoption (D-track, ~4 wks, rides existing releases)
**D1** (rides R2, ~1 wk): metric_definitions + events; register ~15 existing marts; CI guard warn mode; widen observability_registry.surface_kind for 'dashboard' + register surfaces. Deliverable = a complete inventory of every number AWIP shows. **D2** (rides W10 S2/S3, ~1.5 wks): MetricWidget + freshness wrapper; report_kinds/report_runs + renderer scaffolding; migrate deep-audit + reviews (behavioural no-op); CI guard to error. **D3** (rides W10 S6, ~1 wk): export_runs + evented mints; COBie/XLSX migrate; offboarding + DSAR implement against it; export_anomaly sentinel. **D4** (rides FM7, ~0.5 wk): client panels as MetricWidgets behind client_surfaces; the fidelity panel is the reference implementation. **Standing rule (mem://preferences/ at D1):** a number reaches a human through a registered metric, a report run, or an export run — there is no fourth way.
