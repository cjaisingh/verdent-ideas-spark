# AWIP Twin Framework — Estate Twins & the Platform Shadow

**Version:** 1.0 — 4 July 2026 — Status: Proposed. **Thesis:** AWIP runs on two digital twins built from one pattern: (A) the client-facing product — a living data twin of each client's estate; (B) the meta-twin that keeps AWIP evolvable — a shadow environment where every new model, extractor, scorer or routing policy is tested against real historical data and real client-experience traces before touching production. AWIP was accidentally designed for this: every mutation is an event; canonical facts are append-only with supersede; resolver_decisions snapshot thresholds for replay; every embedding stamps embed_model; retrieval contracts pin model+dims; adr-bench records dataset-hashed results; W10 S2.3 ships ingest replay. Twinning is mostly naming and connecting machinery that exists, plus one promotion ladder that doesn't.

## Part A — The Client Estate Twin
**A1 Definition:** the canonical, provenance-complete digital representation of a client's physical and contractual estate: spatial structure (tenant_nodes + part_of edges, via S5 IFC / S6 COBie-CAFM), assets & systems (tenant_nodes + canonical_facts), documents & obligations (lifecycle-governed files + doc_memories), relationships (knowledge graph), behaviour over time (time_series_points via FM12), commercial layer (lease memories + FM8/FM9 facts), identity (Phase 5 resolver), provenance (ingest_events + lineage + anchors). A **data twin, not a geometry twin** — stated plainly; the optional viewer renders, AWIP does not compute on geometry.
**A2 Maturity ladder:** L1 Descriptive (what exists — delivered by W10; programme exit ≈ "L1 twin live for the pilot") → L2 Diagnostic (what's happening and why — S6 reconciliation, FM3 variance, FM12 findings; the twin disagrees with reality out loud) → L3 Predictive (FM4's predictions run against the twin — trained on twin history, evaluated on twin outcomes) → L4 Prescriptive (recommendations dispatched through the Control Plane with operator approval). Each level is a claim a tenant's twin earns — displayed, not asserted.
**A3 Twin fidelity (the honesty instrument):** v_twin_fidelity per tenant — coverage (% known spaces/assets with canonical facts), freshness (fact age vs source cadence; stale-beyond-cadence %), consistency (open conflicts per 1k facts; median conflict age), provenance completeness (% facts with full lineage), sync drift (divergence vs the connected FM tool: export_pending + unimported remote changes). Sentinel twin_fidelity_degraded (medium one metric, high two+). The fidelity panel is client-facing: a twin that admits its gaps is more credible than one that doesn't.
**A4 Synchronisation semantics:** S6 reconciliation IS twin sync, named — import = sensing; conflict triage = state estimation with a human in the loop; export = actuation into the client's system of record. AWIP's canonical layer is truth inside AWIP; the client's FM tool remains their operational system of record until they decide otherwise; every direction evented and idempotent; W7 decision_authorities arbitrate disagreements — the twin inherits governance rather than inventing its own.

## Part B — The Platform Shadow Twin
**B1 Problem:** between now and end-2027 AWIP will swap embedding models (ADR-0006 triggers), upgrade extractors, tune resolver weights, adopt new chat models, change chunking, try rerankers, run predictors. The shadow makes "test against real history and real experience before promotion" the only path to production for anything AI-shaped.
**B2 Core concepts:** **Versioned AI components** — ai_component_versions (component, version, config incl. model id/prompt hash/weights/thresholds, status candidate→shadow→canary→promoted→retired; ai_component_events append-only); retrieval contracts and AI edge fns resolve the promoted version per component at call time — one pin table, rollback = re-pin. **Shadow namespace** — shadow runs write only to shadow_* tables / run_id-partitioned results, never production rows or events; enforced structurally (shadow role lacks INSERT on production). **Replay corpora** — real historical inputs with known outcomes: ingest (re-run raw_records through candidate extractor/chunker — S2.3 generalised to shadow), resolver (re-score resolver_decisions under candidate weights using stored band_thresholds_snapshot; diff = band migrations), retrieval (historical queries against shadow-embedded chunks — embed_model coexistence by design). **Golden sets** — hand-labelled fixtures per component (companion §6 harness generalised), in-repo under e2e/golden/, dataset-hashed. **Experience traces** — experience_traces (tenant_id, surface, input_redacted via the e2e-diag redactor, output_ref, outcome accepted/edited/rejected/escalated/ignored, outcome_source = triage chips / memory tray / edge confirms / client thumbs). The signal already exists; this table makes it replayable. A shadow run answers the same traces under a candidate and diffs against production outcomes: would the new model have produced the answer the human accepted? That is client-experience testing with real data.
**B3 Promotion ladder:** candidate → shadow (replay + golden + trace diff; operator-reviewed report via the HTML pattern: metric deltas, golden precision, experience-agreement rate, cost delta per 1k calls) → canary (small % of live traffic OR one named tenant — tenant-zero is the natural canary; ≥1 week sentinel-clean) → promoted (pinned) → retired. High-consequence components (key_date/obligation extraction, anything feeding FM8 reminders or canonical facts) additionally require the 95%-precision bar AND operator sign-off via approval kind ai.component_promotion. Every transition emits events — the AI stack becomes as auditable as the OKR tree. Cost is first-class in every report.
**B4 Build vs rename:** event replay ← append-only streams (delta: replay drivers); versioned models ← embed_model + pickModel() (delta: registry + resolve-at-call); benches ← adr-bench (shadow adopts the result shape); golden ← §C6 harness (generalise); experience ← existing outcome signals (capture table + redactor reuse); canary ← tenant-zero (per-component split in contract resolution); rollback ← supersede culture (status flip); governance ← approval_queue + gates (one new kind; ISO 42001 testing evidence falls out of shadow reports free).
**B5 Non-goals:** no parallel production stack; no automatic promotion (ladder ends at a human for high-consequence); no synthetic-only evals for promotion; no cross-tenant traces ever; no geometry twin claims.

## Part C — Roadmap integration (T-track)
**T1 — Estate-twin framing & fidelity** (rides W10 S5/S6, ~1 wk): v_twin_fidelity + tenant panel + sentinel; L1–L4 badge; this doc named in docs/. Gate: honest fidelity panel at W10 exit. **T2 — Shadow foundation** (rides R3/S3, ~3 wks): ai_component_versions + events + resolve-at-call; experience_traces capture on copilot/tray/edges; first two replay drivers (extractor, resolver); golden runner; shadow report renderer. First real use: the S3 extractor iterates through the shadow — the eval-harness gate and the shadow report are the same artefact. Gate: one extractor version through the full ladder; **ADR-0014 accepted on that evidence**. **T3 — Canary & promotion governance** (rides R5, ~2 wks): per-component canary split; ai.component_promotion kind; rollback runbook; canary_regression sentinel (auto-halts a degrading canary). Gate: one embedding-adjacent change lands through canary, zero incidents. **T4 — Predictive twin loop** (rides FM4): predictors born inside the framework — twin-history trained, held-out evaluated, tenant-zero canaried, baseline-beating promoted. The "prediction" ring completes inside the twin, the only place it could complete honestly. **Standing rule (mem://preferences/ at T2):** no AI-shaped behaviour change reaches production except through the ladder.

## Part D — Why this closes the loop
"Adaptive" without evidence is drift; "prediction" without a twin is guessing. With both twins: new model ships → candidate → replayed against real history → diffed against real client experience → canaried on a real tenant → promoted with an audit trail — while the estate twin gives every prediction a measured, provenance-complete world to be tested in. That is the constellation caption — secure, governed, intelligent — applied to AWIP's own evolution.
